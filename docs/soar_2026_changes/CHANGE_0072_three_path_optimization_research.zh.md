## 1. 背景与动机

经过系统性测试（Test 1–7），我们建立了 MiniCPM-SALA 各配置下准确率的完整图景：

| 测试 | 配置 | 准确率 | 关键发现 |
|------|------|--------|----------|
| 1 | 非量化 + FP8 + 稀疏 | 53.18% | FP8 损害稀疏注意力 |
| 2 | 非量化 + bf16 + 稀疏 (HEAD 含 CHANGE_0070) | 57.11% | CHANGE_0070 回退 |
| 3 | 非量化 + bf16 + 稀疏 (pre-0070) | **83.02%** | 基线确认 |
| 4 | 非量化 + bf16 + 稀疏 (HEAD−0070) | **83.02%** | Bug 修复安全 |
| 5 | GPTQ + FP8 + 稀疏 | 50.36% | GPTQ+FP8 破坏稀疏 |
| 6 | GPTQ + bf16 + 稀疏 | 57.47% | GPTQ 单独破坏稀疏 |
| 7 | GPTQ + FP8 + 稠密 | 78.84% | 稠密模式容忍 GPTQ+FP8 |

**2×2 矩阵（GPTQ 模型）：**

|  | 稠密 | 稀疏 |
|--|------|------|
| **bf16 KV** | ~99.47%（无 GPTQ 基线） | 57.47% |
| **FP8 KV** | 78.84% | 50.36% |

**核心问题：** GPTQ 量化破坏了稀疏注意力的 topk 评分机制，而稠密注意力对 GPTQ+FP8 具有鲁棒性。研究了三条并行优化路径。

**评分公式：** `final_score = (S1×40% + S8×30% + Smax×30%) × C`  
其中 C = 0（相对准确率 < 97%），C = 0.8（97–100%），C = 1.0（≥ 100%）。

## 2. 路径 1：稠密 + GPTQ + FP8 速度优化

### 概念
接受稠密注意力（GPTQ+FP8 下 78.84% 准确率），专注于通过运行时调优和内核优化最大化吞吐量。

### 关键发现（子代理研究）

**调用链：** `ModelRunner → MiniCPMForCausalLM → MiniCPMDecoderLayer × 32 → GPTQ Marlin GEMM + FlashInfer attention`

**主要瓶颈：**
1. 注意力后端选择：运行时间的 15–25%
2. Marlin GEMM 内核配置：10–20%
3. KV 缓存 FP8 反量化开销：5–10%

**优化阶段：**

| 阶段 | 行动 | 工作量 | 预期收益 |
|------|------|--------|----------|
| A（快速收益） | CUDA graph 调优、`chunked_prefill`、`max_running_requests`、`schedule_conservativeness` | 1–2h | 5–15% 速度 |
| B（内核） | KV 反量化融合、Lightning vs 稠密权衡 | 4–8h | 10–20% 速度 |
| C（准确率） | 逐层混合精度、扩展 GPTQ 校准 | 8–16h | +1–2% 准确率 |

### 评估
- **工作量：** 低–中（天级）
- **风险：** 低
- **准确率上限：** ~78–80%
- **速度上限：** 稠密快 10–20%
- **关键依赖：** NCU profiling 量化瓶颈

## 3. 路径 2：非量化 + 稀疏 + EAGLE3 推测解码

### 概念
使用非量化模型（83.02% 准确率）配合稀疏注意力，加入 EAGLE3 推测解码实现 1.3–2.2× 吞吐量加速。

### 关键发现（子代理研究）

**关键阻塞：** Lightning Attention 的循环状态计算与 EAGLE3 树验证掩码**不兼容**。

**替代方案：**

| 方案 | 方法 | 加速比 | 风险 | 工作量 |
|------|------|--------|------|--------|
| A | 平坦草稿（无树） | 1.3–1.5× | 低 | 3–4 周 |
| B | 分支状态跟踪 | 1.5–2.0× | 高 | 6–8 周 |
| C | 草稿中跳过 Lightning | 1.4–1.8× | 低 | 4–5 周 |
| D | 算法创新 | 2.0–2.5× | 极高 | 8+ 周 |

**额外需求：**
- 训练草稿头：~50K–100K 样本，12–24h 训练
- 草稿头大小：~50–100MB
- 关键参考文件：`llama_eagle3.py`、`hybrid_linear_attn_backend.py`

### 评估
- **工作量：** 极高（6–9 周）
- **风险：** 高（Lightning Attention 阻塞）
- **准确率上限：** ~83%（C=1.0 档可能）
- **速度上限：** 1.3–2.2× 吞吐量
- **关键依赖：** 训练基础设施、Lightning Attention 解决方案

## 4. 路径 3：修复 GPTQ + 稀疏不兼容性

### 概念
修复 GPTQ 破坏稀疏注意力的根因——精度敏感的 topk 评分——通过低工作量改动恢复准确率，同时保留 GPTQ 压缩和稀疏速度优势。

### 根因分析（子代理研究）

**误差传播链：**
1. Q 投影：GPTQ int4→bf16 反量化引入 ~1–2% 逐元素误差
2. K 投影：同样的 GPTQ 误差，加上可选的 FP8 量化额外误差
3. K 压缩：`compress_k_to_scratch_kernel` 在 `kernel_size=32` 个 token 上平均 K — 有帮助但未消除误差
4. 分数计算：`infllmv2_attn_stage1` 计算 `Q @ K^T / sqrt(head_dim)` — 误差放大（sqrt(128) ≈ 11.3× 倍增器）
5. TopK 选择：从 ~2000 个候选中选 `topk=8`（0.4% 选中率）— **二元赢者通吃，不容忍分数误差**

**为什么 NIAH 崩溃（100%→37%）：** 针（needle）必须在精确的 top-8 块中。GPTQ 误差使分数偏移 3–5%，针块容易落出 top-8。

**为什么 FWE 鲁棒（97–98%）：** 事实冗余分布在多个块中，即使 top-8 错误也能包含部分相关块。

### 提议方案

| 方案 | 工作量 | 预期准确率（从 57.47%） | 速度影响 |
|------|--------|------------------------|----------|
| **1. 增大 topk（8→16）** | 1–2h | →70–75% | −10–15% |
| **2. FP32 评分** | 2–3h | →80–85% | −5–10% |
| **3. GPTQ 时禁用稀疏（回退）** | 1h | →78.84%（稠密） | 稠密速度 |
| **4. topk=16 + FP32 组合** | 3–4h | →85%+ | −15–20% |

**实现细节：**

**方案 1（增大 topk）：** 在 `minicpm_backend.py` 中修改 `self.sparse_topk = topk + (window_size // block_size)` → 将 topk 值翻倍。

**方案 2（FP32 评分）：** 在 `minicpm_sparse_utils.py` 的 `infllmv2_attn_stage1()` 调用前，将 Q 和压缩 K 转换为 float32。将评分计算误差从 3–5% 降到 0.3–0.5%。

**方案 3（稠密回退）：** 检测 GPTQ 配置后自动设置 `--force-dense-minicpm`。

### 评估
- **工作量：** 极低（1–4 小时）
- **风险：** 低
- **准确率上限：** ~80–85%
- **速度上限：** 稀疏速度（快于稠密，减去 topk 开销）
- **关键依赖：** 无 — 可立即测试

EAGLE3 理论收益最高，但 Lightning Attention 阻塞使其高风险。除非剩余时间充足否则推迟。

**快速组合：** 路径 3 恢复 GPTQ+稀疏到 ~83% + 路径 1 速度调优 → 无需 EAGLE3 即可获得竞争力分数。
